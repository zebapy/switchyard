TL;DR The happy path

For a solo dev, keep it light: short-lived branches off main, squash-merge via PR, and let a version-tag drive the release. Everyday work and release work are two separate loops.

why this shape

main is always shippable. A release is just "main, frozen at a tag." Drafts mean users never get a half-baked build — the updater ignores drafts until you publish.

1 Versioning — one source of truth

Today the version lives in three files and must agree: package.json, src-tauri/tauri.conf.json, src-tauri/Cargo.toml. Three places to forget = shipped mismatches and a broken updater diff.

the trap

The auto-updater decides "is there an update?" by comparing the running app's version against the version in latest.json — which comes from tauri.conf.json. If you tag app-v0.2.0 but forget to bump the config, the release is built as 0.1.0 and no one updates.

Collapse it to one file

Tauri 2 lets version in tauri.conf.json be a path to a package.json. Point it there and the app version always tracks npm:

// src-tauri/tauri.conf.json
{
  "version": "../package.json",   // reads version from package.json
  ...
}

Now Cargo.toml's version is just the Rust crate version — it does not affect the app/updater version, so you can leave it or bump it loosely. Bump everything with one command:

# bumps package.json, makes a commit + git tag vX.Y.Z (we override the tag name below)
pnpm version minor # 0.1.0 -> 0.2.0
note

pnpm version creates a v0.2.0 tag by default. You use the app-v prefix, so either configure git config tag.prefix isn't a thing — instead run pnpm version --no-git-tag-version and tag manually (see §4), or accept the extra tag. Cleanest: --no-git-tag-version, commit, then tag app-vX.Y.Z yourself.

SemVer for a desktop app

BumpWhenExample
patchBug fixes, no behavior change users must learn0.1.0 → 0.1.1
minorNew features, backward-compatible0.1.1 → 0.2.0
majorBreaking changes (data format, removed features). Pre-1.0 you can treat minor as your "breaking" lever.0.x → 1.0.0

Pre-1.0 convention: stay on 0.x until the app is stable enough that you'd promise compatibility. Bump minor for features, patch for fixes, and don't agonize.

2 Branching model

Use GitHub Flow (trunk-based), not Git Flow. Git Flow's develop/release/hotfix branches are overkill for one person shipping a desktop app.

BranchRoleLifetime
mainAlways shippable. Every commit could be released.forever
zebapy/<topic>One feature/fix. Branch, work, PR, merge, delete.hours–days
your convention

You already prefix branches with your GitHub handle (zebapy/drag-reorder-fix). Keep it — it reads well and namespaces cleanly. Use full words: zebapy/git-panel-redraw, not zebapy/gp-fix.

Rules of thumb

  • Short-lived. A branch open for a week drifts from main and merges painfully. Merge or rebase daily.
  • One concern per branch. The worktree-speedups merge that rode into your last release is the smell — bundle deliberately, not accidentally.
  • Don't commit straight to main for anything non-trivial — even solo, the PR is your review + CI gate + changelog entry.
  • Tags are not branches. app-v0.2.0 points at a commit on main. Never branch off a tag unless you're doing a hotfix on an old release (§7).
git worktrees fit you

You're literally building a worktree app — use them. git worktree add per feature lets you keep main checked out for releases while a feature cooks elsewhere, no stash-dance.

3 PRs & CI gates

The PR is where quality is enforced cheaply. Add a CI workflow that runs on every PR (separate from the release workflow) so nothing merges red.

Minimum PR checks (.github/workflows/ci.yml)

name: CI
on: { pull_request: { branches: [main] } }
jobs:
  check:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 10.26.1 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }
      - uses: dtolnay/rust-toolchain@stable
        with: { components: clippy }
      - uses: swatinem/rust-cache@v2
        with: { workspaces: src-tauri -> target }
      - run: pnpm install --frozen-lockfile
      - run: pnpm check            # tsc --noEmit
      - run: pnpm build            # vite build must succeed
      - run: cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings
      - run: cargo fmt --manifest-path src-tauri/Cargo.toml --check
cost note

A full Rust compile per PR is slow + uses macOS minutes. swatinem/rust-cache helps a lot. If it bites, run cargo clippy on a cheaper ubuntu-latest runner — clippy doesn't need the Tauri bundle, just the crate to type-check.

Branch protection on main

Even solo, turn on: require CI to pass before merge, require branches up to date, and require linear history (forces squash/rebase, no merge bubbles like the one that snuck into your release). Settings → Branches → add rule for main.

Merge strategy: squash

Squash-merge so each PR = one clean commit on main with a conventional title. Keeps main readable and makes changelog generation trivial (§8). Delete the branch on merge.

4 Cutting a release — step by step

This is the exact sequence. Everything after the tag push is automated by your release.yml.

# 0. Be on a clean, up-to-date main
git switch main && git pull

# 1. Bump version (package.json is source of truth; no auto-tag)
pnpm version minor --no-git-tag-version

# 2. Commit the bump
git commit -am "chore(release): v0.2.0"

# 3. Push main FIRST (so the tagged commit exists on the remote branch)
git push origin main

# 4. Tag that commit with your app- prefix, push the tag
git tag app-v0.2.0
git push origin app-v0.2.0   # <-- this triggers release.yml
version must equal tag

The number in package.json (→ tauri.conf.json) must match the tag. Tag app-v0.2.0 ⇄ app version 0.2.0. Mismatch = confusing release + the updater compares the wrong number.

After CI finishes

  1. CI produces a draft GitHub Release with the universal .dmg, the .app.tar.gz + .sig, and latest.json.
  2. Download the .dmg and actually run it. Launch, click around, confirm it opens (you'll get the Gatekeeper warning since it's unsigned — that's expected).
  3. Publish only when happy: 
    gh release edit app-v0.2.0 --draft=false --latest
the moment users update

Publishing flips releases/latest to this release. Existing installs hit your updater endpoint, see 0.2.0 > 0.1.0, download, and relaunch. Until you publish, they stay on the old version. That's your safety valve.

5 Release channels (stable vs beta)

Optional, but the right way to test risky releases on yourself before everyone gets them.

ChannelHowUpdater endpoint
stablePublished, not pre-release. releases/latest resolves to it..../releases/latest/download/latest.json
betaMark the GitHub release as pre-release. releases/latest skips pre-releases, so stable users are unaffected.a separate latest-beta.json the beta build points at

Simplest version: tag betas like app-v0.2.0-beta.1, set prerelease: true in the action for those tags, and run a beta build of the app whose updater endpoint reads the beta feed. For a solo project you may not need this until you have real users — draft + self-test (§4) covers most of the risk.

6 Updater traps specific to your setup

  • Drafts are invisible to the updater — releases/latest/download/latest.json only resolves on a published release. Good (safe), but means you must remember to publish or no one updates.
  • Pre-releases are skipped by /latest too. A beta won't accidentally ship to stable users.
  • The minisign key is forever. TAURI_SIGNING_PRIVATE_KEY signs every update; the public key is baked into shipped apps. Lose it and you cannot push updates to existing installs — they'll reject the signature. Back it up (password manager), never rotate casually.
  • Version only goes forward. The updater installs if latest.json version > installed. You can't "downgrade" users via the updater — to undo a bad release, publish a higher version with the fix.
  • Unsigned + updater works because the minisign signature (not Apple's) is what the updater verifies. Your ad-hoc signingIdentity: "-" is fine for this.
bad release recovery

Shipped a broken 0.2.0? Don't delete it (users already pulled it). Fix on main, cut 0.2.1 immediately. The updater pulls everyone forward. Optionally delete the broken release assets so new downloaders don't grab it, but the version-forward fix is the real remedy.

7 Hotfixes

Because main is always shippable, a hotfix is just a fast trip through the normal loop:

  1. zebapy/fix-crash off main → fix → PR → squash-merge.
  2. Bump patch (0.2.0 → 0.2.1), tag app-v0.2.1, push.
  3. Publish the draft → updater ships it.

You only need the "branch off an old tag" dance if main has moved on with changes you don't want in the hotfix. Rare for a solo dev — usually main is where you want the fix anyway.

8 Automate the boring parts

Conventional commits → changelog

You already write feat: / fix: / ci: / chore: commits. That unlocks auto-changelogs. Two good options:

ToolWhat it doesGood when
release-pleaseWatches main, opens a "Release PR" that bumps the version + writes CHANGELOG.md. Merge it → it tags → your release.yml fires.You want fully hands-off versioning & changelog.
git-cliffGenerates a changelog from commits on demand; you still tag manually.You want a changelog but keep manual control of when to release.
recommendation

Start manual (§4) — it's 5 commands and you learn the moving parts. Add release-please once cutting releases feels like a chore. It also fixes the "match the version in 3 places" problem by owning the bump.

Put release notes in the GitHub Release

Right now your releaseBody is static text. Swap to GitHub's auto-generated notes (it lists merged PRs since the last tag) by removing releaseBody and adding generateReleaseNotes: true — or let release-please own it.
